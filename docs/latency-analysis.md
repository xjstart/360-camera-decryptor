# 播放与录制延迟分析（2026-09-07）

## 2026-09-08：录制异常回归修复

用户提供的 `manual-2026-09-07_10-40-02-1c925f6c.mp4` 经 ffprobe 检查为 370764 字节、
容器时长 5.377333 秒、640×360 H.264 视频 49 帧（4.083333 秒）及单声道 AAC。
文件可以解码，但不包含预期约 58 分钟的内容。浏览器后台暂停提示不能解释录像端缺失。
原文件未作改动；缺失时段无法从该文件补回。

本次复现并修复：

- **EOF 提前结束：** 60 秒合成 FLV 在上一版只能输出约 25 秒。
  原循环只检查 JS 输入队列和背压，没有排空 WASM 内部缓冲。
  现在区分需要输入、解码有进展、背压和结束，持续排空至解码器要求新输入；60 秒样本输出完整 720 帧。
- **固定帧率导致双管道等待：** 25 fps 输入直接标为 12 fps 原始视频会拉长视频时间线，
  与音频分离；上一版临界缓存背压会使解码停在 74 帧附近，视频待写队列不再下降。
  现在按视频源时间戳采样到显式输出 fps，高帧率取样、低帧率重复已有帧，保持录制时长。
  30 秒 25 fps 输入转为 12 fps 后为 30 秒、360 帧，不再停滞。
  FLV 的毫秒时间戳允许 1 ms 量化误差；倒退或超过 2 秒的跳变明确失败，避免无限补帧。
- **虚假的正常状态：** 管线连续 30 秒无解码/编码入队进展时中止并报告失败；停止时先排空解码和输出帧。
  录像强制停止、异常返回码和已有错误均保留为 failed，页面不再报告正常完成封装。

新增测试包括 60 秒长输入、6/12/25 fps、AAC/G.711 A-law、源无数据超时，以及强制停止状态。
另以实时 HTTP 合成源运行公共 TS → 播放 fMP4 / 录制 MP4 全链路：
8 秒时停止播放，录像继续 15 秒后正常停止，生成三个可读分片，共 **22.759727 秒**，状态为 stopped、无错误。

这些复现说明了代码中的缺陷，但实机拉流在本轮持续超时，尚未确认该摄像机当时的实际帧率，
也没有把合成流验证当作这台摄像机的长时间验收。重启后端并启动新录制后应用这些修改。

## 参数与路径

| 环节 | 修改前 | 本次实现 |
| --- | --- | --- |
| 主页面 Qhww | 已采用官网低延迟配置 | 保留 minDecoderBufferSize=1、waitingPcmDur=50 ms、waitingYuvNum=1、delayTimeLimit=1000 ms、resample=1 |
| 两个实验播放器入口 | 缺省/512 KiB 启动门槛，resample=0 | 与主页面保持上述参数一致 |
| Qhww 日志 | 库 logLevel=2 会输出含密钥的 configure 参数；仅分别看两层缓存 | 库 logLevel=0，页面报告同一音/视频路径的解码+渲染缓存之和，标明不是端到端延迟 |
| FLV 代理 | 16 KiB 凑块 | 4 KiB；禁用 Nginx 响应缓冲 |
| Node/WASM | 固定等到 512 KiB；直接送入网络碎片；resample=0 | 拼接完整 FLV tag 后尽早打开；resample=1；支持配置启动门槛 |
| FFmpeg 原始音视频输入 | 默认分析；视频 nobuffer | 已知原始格式的探测限制；保留探测帧，避免 nobuffer 丢弃录像开头 |
| 公共 H.264/TS | GOP 2 秒；默认 mux 等待 | GOP 1 秒、重复 SPS/PPS；muxdelay/muxpreload=0；flush_packets=1；max_interleave_delta=100000 µs |
| TS → fMP4/录制 | 默认格式探测 | 显式 MPEG-TS；probesize=1 MiB、analyzeduration=1.5 秒，覆盖中途加入时下一关键帧 |
| 播放 fMP4 | 1 秒分片 | 250 ms 分片；及时刷新输出 |
| Python 管道读取 | read(64 KiB) 等待凑满 | read1(64 KiB) 返回当前可读数据；公共 TS 和播放 remux 都应用 |
| 浏览器直播播放 | 无缓冲追赶 | 落后已收数据超过 1.5 秒且可 seek 时跳到尾部前 0.5 秒；无法 seek 时 1.05 倍追赶，恢复后归一 |
| 订阅队列 | 把字节预算换算成固定 64 KiB 块数量 | 按真实待写字节计算，适应 read1 的小块；录像 EOF 使用独立位置，满队列也保留尾部 |
| Node 录像停止 | 直接结束 stdin，可能丢失待写帧 | 先排空已接受的音视频帧，再结束输入；超限或编码错误明确失败 |

`delayTimeLimit` 是播放器缓存追赶目标，不是摄像机到画面的总时延保证。
Qhww 源码会在缓存大于约 1.414 倍该值时逐渐加速。继续降低此值需要实机网络抖动数据。
后端仍经过 WASM 解码、H.264/AAC 编码、TS 和 fMP4 封装，比浏览器直接解码多了处理步骤。

FFmpeg 参数语义参见 [官方格式文档](https://ffmpeg.org/ffmpeg-formats.html)：
`probesize`、`analyzeduration` 控制探测预算；`flush_packets` 控制输出刷新；`frag_duration` 使用微秒。
减小探测窗口必须保留识别视频参数的时间，而非越小越好。

## 本次复现的重要问题

1. 仅喂入 13 字节 FLV 文件头时，WASM `_openDecoder` 返回 8；直接继续 `_sendData` 会返回 -1。
   现在先收齐流头、需要的音频信息和首个完整视频包。若仍返回 8，则重建原生实例并重放保留的启动数据，
   随新数据逐步重试，最多回退到原有 512 KiB 范围；其他错误直接上报。
2. 把 4 KiB 网络块直接送入 WASM 可能截断 NAL，出现 open 成功但宽高为 0、最终只有音频的情况。
   按完整 FLV tag 喂入后，同一输入完整输出 48 个视频帧。FLV 头、长度、PreviousTagSize 和 tag 内存上限均会检查。
3. TS 探测设为 0.5 秒/64 KiB 时，从 GOP 中部加入会因未收到 SPS/PPS 而报 `dimensions not set`。
   最终采用 1.5 秒/1 MiB，并以 5 个不同的非对齐字节位置接入验证。
4. 录像结束标记以前可能等待 1 秒后清空满队列；现在不等待消费者腾位置，不因写入 EOF 丢掉尾部。
   编码器停止也等待 drain 后的已接受帧，首个视频帧前到达的音频会暂存后写入。

## 验证结果

- **按实时节奏发送的本地 FLV：** 160×120、12 fps、单声道 AAC，22 秒共 762097 字节。
  对相同输入运行基线和修改后 Node/WASM/FFmpeg，测量启动进程到 stdout 首个 TS 数据的时间：
  **15.594 秒 → 0.406 秒**。这是一次本地合成流启动对比，不是玻璃到玻璃延迟，也不含 Python remux/浏览器缓冲。
- **媒体完整性：** 4 秒、48 帧 FLV（小于 512 KiB），分别以 13/4096/65536 字节输入；三个结果均为 48 帧且含 AAC。
  音视频时长差小于 0.2 秒。转换为播放 fMP4 后仍为 48 帧，MP4 分片录像合计也是 48 帧。
- **共享源加入：** 5 个中途接入位置均能生成可解码的 fMP4。
- **生命周期：** 小于 64 KiB 的管道写入会在进程结束前送达；实际字节限额、满队列保尾、播放停止不打断录制、
  刷新播放保留录制旧源等测试通过。
- **前端：** 追赶、不可 seek 的温和加速、暂停/seek 保护均有 Node 回归测试；JS 语法检查通过。
  因浏览器调试接口不可用，未完成真实浏览器画面对比。

## 实机验收与限制

在同一摄像机、同一清晰度下同时比较官网、Qhww 和后端画面的摄像机时间戳，记录首次画面时间及稳定播放后的差值，
再测试播放中开始录制、录制中刷新播放和停止录制后最后一段可播放性。
缓冲日志只描述已到达本机的数据，不能反映摄像机、云端转发或网络路径的全部积压。

后端输出 fps 仍由参数指定（页面默认 12）；9 月 8 日修复后，视频按源时间戳采样到这一输出帧率。
音频仍按连续 PCM 样本编码；长时间音画同步和摄像机断流恢复需要实机验证。
媒体测试覆盖 H.264/单声道 AAC 与 G.711 A-law，其他机型的私有 tag、音频格式和 HEVC 需要实机补充验证。
一秒 GOP 和较小输出分片会增加关键帧/封装开销；保存用 MP4 分片时长仍由原录制配置控制。

启动门槛可通过 `server.decrypt_min_decoder_buffer_size` 调整；缺省为 1，完整 FLV 包检查始终生效。
需要保守回退时可设为 524288。运行中的公共源会保留启动时的配置，新源启动后应用新值。
